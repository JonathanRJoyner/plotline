# Model runtime

**Decided:** 2026-10-16

**Choice:** Designed on 2026-10-16 with [learned line models](2026-10-16-learned-line-models.md): tract (MIT or Apache-2.0) behind a `ModelRuntime` trait in the core, natively in a new `crates/models`, and in the browser as a separate WebAssembly module built with SIMD, fetched when a model is first downloaded, loaded or restored and called synchronously from the engine through the worker. Built on 2026-10-17: the model module is 8,310,634 bytes (2.39 MB gzipped), under a CI limit of 9,000,000 (8,309,831 bytes when the runtime was first built on 2026-10-16). The engine module is 2,203,052 bytes (0.84 MB gzipped), measured on 2026-10-17 against its limit of 2,300,000. It was 2,015,556 bytes on 2026-10-16, when the bridge to the model module was added; the growth since is not attributed. SIMD comes from `crates/models/.cargo/config.toml`, which only the model module's build reads, and `opt-level = "s"` covers the twelve crates that make up its size: tract's but `tract-linalg`, `ndarray`, `rustfft`, `prost`, `nom` and `plotline-models` itself. The worker holds later commands until an `addModel` has loaded the module and run.

**Reason:** tract inside the engine module would take every visitor's download from 0.75 MB to 4.1 MB gzipped (the spike of 2026-10-16, in the spec's measurements); on its own, size-tuned, it is 2.4 MB gzipped, fetched only by those who use a model, and 0.7 MB smaller than a second engine build with tract. SIMD runs the models about four times faster. One engine serves every front end, and the algorithm stays in the core. A `RUSTFLAGS=` prefix in the npm script fails in the Windows shell npm uses, and a workspace-wide flag would put SIMD in the engine module too. Setting the module's other crates to "s" as well saves only 28 KB more. Holding commands keeps their order, so a command sent right after `addModel` sees the model.

# Embedded presets

**Decided:** 2026-10-16

**Choice:** Added on 2026-10-16 under [the embedded presets spec](../superpowers/specs/2026-10-16-embedded-presets-design.md). A drawing carries the preset of the run that made it (`Drawing.preset`), which the runner builds from the run's own style, settings, canvas and pens with a null machine. `Session::svg()` and `json()` embed it with the machine the session has at export time. The SVG holds it in `<metadata id="plotline-preset">` on the line after the opening tag, as compact JSON with `&`, `<` and `>` written as entities. The JSON paths format gains an optional top-level `preset` key and its `version` stays 1. `presets::from_text` reads a preset, an exported SVG (stripping a CDATA wrapper an editor added) or an exported JSON drawing, and `Session.load_preset`, the CLI's `--preset`, the MCP `load_preset` tool and the GUI's Load preset (`.json` and `.svg`) all use it. G-code and PNG exports carry no preset, and nothing leaves the block out

**Reason:** An export did not record how it was made, so a setup came back only if a preset was saved too. The run's own snapshot is embedded, not the session's state, because settings can change while a run is under way and a budget fit leaves the session's settings alone while its drawing comes from a trial value; the file then always matches the drawing it holds. A run holds no machine, so the session fills in its own at export time, and loading the file later keeps the user's machine rather than clearing it. `<metadata>` is plain SVG with no vendor namespace, so it keeps the naming rule (§12, question 1), and entity-escaped JSON is valid XML whatever a pen is called. An optional key keeps the format at version 1, since a reader that ignores unknown keys reads the file as before, and the exporters write nothing extra without a preset, so the golden files did not change. One function that accepts all three kinds gives every front end a single "load this file" action.
